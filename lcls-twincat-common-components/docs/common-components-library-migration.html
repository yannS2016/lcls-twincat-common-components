Context

The common-components device FBs (FB_PPM, FB_ATM, FB_WFS, FB_GBS, FB_IPM, FB_LIC, FB_REF, FB_XPIM, FB_SLITS_POWER, FB_SXR_SATT_Stage, and now FB_KBO_Coating_States / FB_Coating_States_NoPMPS) are thin wrappers over the lcls-twincat-motion-abstraction (ND) state-mover stack. This page describes the interface and how to initialize a device in a production PRG.

What Changed

  • The integration PRG owns the motion primitives. Axes, persistent storage, the motion stages, the position-state slots, the fast-fault output and the arbiter are all declared in the PRG, not inside the device.
  • Devices receive dependencies by FB_Init REFERENCE TO. The device forwards them into its internal FB_PositionStatePMPSND (or FB_PositionStateND) and re-forwards the enum bridge and run-time toggles each cycle. No device owns an AXIS_REF.
  • Per-state config lives in the PRG via an FB_CC_StatePMPSConfig array (position + PMPS state key + a stDefault baseline), or FB_CC_StatePMPSEncConfig for raw-counts devices (see below). The device layers its own per-state name/fDelta defaults on top.
  • Non-state motors moved to the integrator. Legacy X/Z/Zoom/Focus axes are no longer owned by the device; declare and wire them in the PRG.
  • State movers carry no motion parameters. ST_PositionState has no fVelocity/fAccel/fDecel fields. Set them once per stage with SetMotionParam/SetVelocity on the motor; every state-move on that stage uses whatever is currently set, regardless of target state (see the Notes section for the one case that needs more than this).

Power Slits (FB_SLITS_POWER)

Blade-aperture device, not a state mover: four blade motors indexed by E_SlitsBlade, eight RTDs and a flow switch. M_UpdatePMPS(index) runs each cycle to snap the requested gap into the PMPS envelope; index is the device's slot in the aperture table. The fApertureMargin FB_Init input (mm, default 0.01) is the amount trimmed off the authorized width/height when snapping the request into compliance. Terminal links for the RTDs sit in the instance TcLinkTo pragma.

Solid Attenuator (FB_SXR_SATT_Stage)

Single-axis filter-stack mover (states OUT + FILTER1..8) built on FB_PositionStateND, not a PMPS state mover. It uses FB_CC_StateDefaultsConfig (position + name, no PMPS key) for the states and pulls only an RTD reactive-temp setpoint from the DB via RTDPMPSState. Per-filter material/thickness is written into the device's arrFilters table by an FB_SATT_FilterConfig array. Beam energy PMPS_GVL.stCurrentBeamParameters.neV feeds the transmission calc; keep it non-zero to avoid a divide-by-zero in the physics library.

Coating Selector, PMPS + Raw Counts (FB_KBO_Coating_States)

Single-axis, 2-state mirror coating selector (Si/B4C) built on FB_PositionStatePMPSND. Unlike FB_PPM above, its states are raw encoder counts, not scaled positions: Si and B4C are different physical encoder targets, so the per-state config uses FB_CC_StatePMPSEncConfig (not FB_CC_StatePMPSConfig) to supply a distinct nEncoderCount per state.

Simpler 2-state coating selector with no beam-safety gating, built on FB_PositionStateND directly. All per-state config, including sName, is integrator-owned via FB_CC_StateDefaultsConfig — the device FB owns nothing.

Notes

  • Config-before-device. Tick the FB_CC_StatePMPSConfig / FB_CC_StatePMPSEncConfig / FB_CC_StateDefaultsConfig array before the device each cycle; the device's per-state defaults overwrite the baseline FB_StateSetup just laid down.
  • Multi-motor state movers size the aiMotionStage array to the active motor count and set nActiveMotorCount accordingly (see the motion-abstraction PRG_PMPS test program for a 4-axis example).
  • Multi-stage devices with a single state stage. Several devices carry more than one physical stage while only one drives the internal state mover. FB_ATM, for example, has an X alignment motor alongside the Y state stage; FB_IPM, FB_WFS and FB_XPIM likewise pair their state stage with aux X / Z / Zoom / Focus stages. Wire only the state stage into aiMotionStage (slot 1, nActiveMotorCount := 1) and give it the astPositionState row. Each auxiliary stage is a plain caller-owned FB_MotionStageNC that the PRG (or test harness) declares, configures and ticks on its own every cycle; it never appears in aiMotionStage or astPositionState. The device sizes aiMotionStage to MotionConstants.MAX_STATE_MOTORS to match FB_Init's fixed-size signature, so the unused slots stay nil and are never touched.
  • Commanding moves: write fbPPM.eEnumSet := E_PPM_States.YAG1; and read back fbPPM.eEnumGet.
  • Raw-counts devices don't get fPosition from the integrator. FB_PositionStateInternalND recomputes it every cycle from nEncoderCount via the axis's live NC scaling factor. Writing fPosition alongside nEncoderCount on a bUseRawCounts := TRUE state gets silently overwritten next scan — don't do it.
  • Speed that varies by destination state has no framework support. The deprecated FB_TM1K4_States used a different speed for OUT than for any TARGET, selected automatically off the old state struct. Nothing in the ND framework reproduces this; a device that genuinely needs it has to watch the commanded goal and call SetMotionParam conditionally on every goal change, not once at init.
  • No runtime-configurable state count. Every device here hardcodes its own state count and enum (1 to 16 states across the library) and gets cloned for a new device, rather than one FB flexing at runtime. Dropping to a generic UINT selector would lose the EPICS mbbi/mbbo dropdown (ZRST/ONST…) that operator screens rely on.
